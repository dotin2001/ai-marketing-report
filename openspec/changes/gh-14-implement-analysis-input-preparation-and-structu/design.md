## Context

See `proposal.md` and the capability spec. Stage #13 left `backend/app/ai/` empty and `backend/app/jobs/analysis_worker.py` with an unavailable production executor. The worker already validates semantic and numeric identities, then writes `AnalysisResult` and section items. `AnalysisJob` captures dataset, metric-set, draft, and revision IDs; metric rows and input totals have owner-scoped references. Existing result-reference tables can link items to metrics. The public job detail already has the five section names and provenance fields.

## Goals / Non-Goals

**Goals:** Make input preparation deterministic and bounded; provide a strict provider-independent response model; validate numeric grounding and provenance before the existing completion transaction. Keep the worker's durable state machine and public contract intact.

**Non-Goals:** Call OpenAI, add a live prompt or provider transport, generate narrative in production, infer KPIs from prose, or change report/PDF/frontend behavior. A deterministic fake may exercise the validation path in tests; the production executor continues to fail safely until a separate provider change wires it in.

## Decisions

1. **Prepare from captured database identities.** Add an AI-layer preparation service called after worker claim. Query report, confirmed dataset, metric set, metric results and their exact input totals, and ordered draft objectives with owner/report filters. Require the report's current dataset/metric references, draft ID and both revisions, inclusive period, and recomputed semantic identity to match the claimed job. Sort metrics by stable scope/group/currency/name/ID and objectives by ordinal. Serialize decimals as strings. This uses the existing provenance graph; an alternative serialized job payload would allow stale or tampered numbers and leak customer content through Redis.
2. **Fail closed on context limits.** Start with a maximum of 20 objectives, 1,000 characters per objective, 200 metric records, and 64 KiB for the canonical prepared JSON; keep these constants versioned in the AI layer and documented. Fetch one extra row to detect overflow. If any limit is exceeded, fail the attempt with a sanitized, non-retryable `provider_unavailable` outcome until inputs change or the budget is deliberately revised. Do not silently omit metrics, because omissions could make a conclusion seem complete. Optional source excerpts and draft claims are excluded in this stage; when later added, they must be separately bounded and delimited as untrusted data. Objectives are also untrusted user text and must remain data in the future prompt template.
3. **Model the response in five explicit arrays.** Use strict Pydantic models in `backend/app/ai/` with `extra='forbid'`, bounded item counts/content, a required nonempty summary, optional empty remaining arrays, unique ordinal per section, and explicit classification. A `data_gaps` field carries data limitations to match the existing API and DB enum. Keep model ID, prompt version, request provenance, and input identities outside provider-authored content; the trusted adapter supplies them after validation. A single free-form JSON blob would weaken section and provenance checks.
4. **Keep numeric assertions structured.** Each item has zero or more metric-reference IDs and optional structured numeric assertions whose value/unit/scope/period/currency must equal the cited available metric. Unavailable references may only describe limitations and their stored reason. Reject numeric literals in free-form narrative content and require numbers to travel through validated assertions; this conservative rule avoids trying to prove arbitrary prose true with regex matching. Convert accepted sections into existing `AnalysisItem` rows and use `AnalysisItemMetricReference` for cited IDs in the same result transaction. Existing public text stays number-free; computed metrics are already separately available through their API. A future presentation change can render cited values from structured references. No `AnalysisResult` row is committed for invalid output.
5. **Preserve worker failure and retry semantics.** Refactor the worker's runner boundary to accept a prepared context and a parsed response, with a deterministic fake for tests. Recheck captured identities immediately before completion using the existing domain/repository transition. Map schema and grounding failures to non-retryable `invalid_structured_output`, stale data to `stale_result`, and preparation budget or missing dependency to a sanitized existing failure code. Never log the context, raw response, or exception text. A new public failure code would require a contract change; this stage uses established codes.

## Risks / Trade-offs

- **Strict numeric-text rule limits natural prose** → Keep computed numbers in structured assertions and metric API data; test date, percentage, currency, and digit-bearing text rejection so behavior is predictable.
- **Large campaigns may exceed the 200-metric budget** → Fail explicitly before a provider request and document the limit; revise it only with measured token and performance evidence.
- **Objectives are mutable and are not snapshotted on the job** → Require exact captured draft/objectives revisions and current semantic identity at preparation and completion; never reconstruct an older revision from newer text.
- **Existing worker writes items but not metric-reference links** → Extend the completion transaction to write validated links atomically; verify duplicate delivery cannot duplicate links. Use an Alembic migration only if a proven database constraint is missing.

## Migration Plan

No schema or public API migration is expected. Add the input and response models, then wire validation into the worker without enabling provider calls. Rollback restores the existing unavailable executor path; persisted jobs and results retain their current schema. Document the AI context limits and any new configuration only if introduced during implementation.
