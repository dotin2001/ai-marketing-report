## Context

See `proposal.md` and `specs/version-linked-pdf-export-jobs/spec.md`. `ReportVersion` already stores a snapshot, SHA-256 identity, and template version. `backend/app/pdf/` validates and renders that saved envelope. The database already has export/attempt tables, binding constraints, create/claim/finish/fail/retry helpers, and `AssetServices.store_generated_pdf`; the download route already reauthorizes and verifies stored bytes. Export command routes, a PDF worker, and PDF recovery are absent. The current PDF object key is stable per export, which needs care if retries produce different PDF bytes.

## Goals / Non-Goals

**Goals:** Reuse the existing version, renderer, export persistence, storage, and download boundaries. Make every accepted command and worker attempt durable, owner scoped, and safe under repeated HTTP requests or Celery delivery.

**Non-Goals:** Create a version automatically, render from an active draft, alter the snapshot format or PDF template, build frontend controls, or introduce a generic job framework before two implementations justify it.

## Decisions

1. **Use one version-bound domain service for the public commands.** Resolve the report and version with owner predicates before template, key, or state errors. Validate the requested template against the version's template, derive `sha256(snapshot_identity || template_version)`, and use the existing `(version_id, snapshot_identity, template_version)` uniqueness for one logical export. Apply the established scoped idempotency record and request fingerprint for create/retry, including replay headers. Retry checks the current immutable input identity, last attempt ordinal, failed/retryable state, and a separate retry key under a row lock. Return `202` for create/retry; provide signed, owner/report/version-bound keyset pagination for list and a safe detail projection for attempts. Alternative: make routes mutate ORM rows directly; that would scatter authorization, idempotency, and lifecycle rules.
2. **Publish after commit and reconcile from PostgreSQL.** Creation or retry commits its queued attempt before a best-effort Celery send. A bounded recovery pass republishes queued PDF attempts so a broker outage after commit cannot strand them. The worker claims by owner/report/export and current ordinal, snapshots only the selected `ReportVersion`, renders it through `PdfRenderer`, then calls the asset service to finish. Duplicate delivery loses the claim or sees a terminal attempt. Alternative: publish inside the transaction; a worker could run before commit or a rollback could leave orphan work.
3. **Keep the render/storage/finish boundary retry safe.** `SavedVersion.from_record` copies the immutable record before rendering. `AssetServices` verifies the upload and transactionally attaches a `FileAsset` to the matching running export. Use an attempt-scoped private storage key (trusted owner/report/version/export/ordinal segments) for generated bytes so a failed upload or changed PDF metadata from an earlier attempt cannot conflict with a later retry. The succeeded asset remains the sole export target; compensate newly written unbound objects on failed DB completion, and reconcile an already linked matching asset after uncertain commit. An orphan from a crash is never downloadable and can be cleaned through a bounded storage lifecycle. Alternative: reuse the existing export-stable `report.pdf` key for every attempt; a failed prior write can block a valid retry if bytes differ.
4. **Persist explicit safe failure and recovery outcomes.** Map renderer codes to `invalid_snapshot`, `render_failed`, or `artifact_validation_failed`; map storage failures to `storage_unavailable`. Unexpected worker faults use a generic `render_failed` or `storage_unavailable` classification at the failing boundary. Never persist exception text, HTML, source content, object keys, or credentials. A stale running attempt is failed by a timeout recovery pass only when its ordinal and state still match; a later completion cannot overwrite the failure or a newer attempt. Use finite PDF task and stale thresholds consistent with the renderer timeout, with settings and example environment documentation. Alternative: rely on Celery result state; Redis is not the authoritative status store and does not preserve the version binding.
5. **Extend the public contract without exposing storage internals.** Add strict Pydantic create/retry, summary/detail, attempt, file, and page schemas. The detail includes safe timestamps, failure code/message/retryability, and successful filename/type/size/checksum/download availability; JSON never returns the object key or signed URL. Preserve the existing `pdf_downloads.py` path and its reauthorization behavior. Update the version summary's latest export projection through the same public shape. Alternative: return ORM or storage metadata directly; it would leak private references and couple the API to persistence.

## Risks / Trade-offs

- [A crash after upload but before DB commit leaves a private unbound object] → Attempt-scoped keys prevent corruption; compensation and bounded orphan cleanup remove leftovers, while downloads require a succeeded DB binding.
- [A delayed worker completes after timeout or retry] → Compare the export state and attempt ordinal in transactional finish/fail; stale completions cannot attach a new asset.
- [The current export list repository loads all rows] → Add a bounded owner/version keyset query before exposing pagination, then test a newly inserted row between pages.
- [A storage or browser outage leaves queued/running work] → Reconcile queued attempts and fail stale running attempts with sanitized retryable status; keep the saved version unchanged.
- [Existing helper behavior may violate the intended invariant under concurrency] → Verify against PostgreSQL and make focused repository fixes; introduce an Alembic migration only for a confirmed schema gap.

## Migration Plan

1. Add schemas, owner-scoped service, routes, worker, attempt-scoped storage behavior, and recovery configuration. Reuse existing tables unless constraint verification proves a migration necessary.
2. Deploy worker/browser/storage configuration before enabling the export routes. Run focused contract, PostgreSQL, deterministic fake-storage and fake-renderer tests, then the backend stage suite and strict OpenSpec validation.
3. On rollback, stop accepting new exports and stop PDF worker delivery; preserve saved versions, persisted export rows, and completed private assets for a later compatible deployment. Do not remove historical version or PDF data.
