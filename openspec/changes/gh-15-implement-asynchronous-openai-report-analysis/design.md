## Context

See `proposal.md` and `specs/asynchronous-openai-report-analysis/spec.md`. Stage #13 supplies persisted, idempotent analysis jobs, attempt claims, reconciliation, retry, and the public job API. Stage #14 supplies `PreparedContext`, strict `StructuredOutput`, numeric grounding, and an injectable `AnalysisRunner`; the production `unavailable_executor` still fails safely. `AnalysisResult` already stores semantic and numeric identities, model identifier, prompt version, and request provenance, while its job stores the captured dataset and metric set. `backend/pyproject.toml`, `app/core/config.py`, and `.env.example` have no OpenAI dependency or settings yet. The existing 300-second task limit and 600-second stale-running threshold constrain request timeout and retries.

## Goals / Non-Goals

**Goals:** Add one backend provider adapter and versioned prompt; keep provider output outside the database until the existing grounding and transactional completion checks pass; make provider failure classes deterministic and safe; verify worker behavior with a fake SDK boundary.

**Non-Goals:** Introduce a new job state, endpoint, database result format, frontend flow, PDF workflow, background mode at the provider, or live-provider tests in the default suite. Celery already provides asynchronous execution, so one bounded Responses request per claimed attempt is sufficient.

## Decisions

1. **Use the async Responses Structured Outputs helper behind an adapter.** Add and lock the OpenAI Python SDK, then call the current async `responses.parse` path with a Pydantic wire model. The [official Python SDK helper documentation](https://github.com/openai/openai-python/blob/main/helpers.md) identifies `responses.parse(..., text_format=...)` and `output_parsed`; recheck the pinned SDK and official guidance during implementation. Inject a narrow async client protocol for deterministic tests. Do not use the provider's separate background mode: Celery and PostgreSQL already own job delivery and status, and a second remote job lifecycle would complicate retry and freshness.
2. **Separate provider wire shape from trusted domain shape.** Define a wire Pydantic model with all five sections and explicit required fields using a JSON-schema-compatible representation of unavailable reasons (a list of metric ID/reason pairs). Convert it to the existing `StructuredOutput` after SDK parsing, then call `validate_output` in the worker. This avoids depending on whether the SDK accepts the existing `dict[UUID, str]` map and defaulted fields as strict provider schema. A parsed object alone is insufficient: numeric references, free-text figures, ownership, and current semantic identity still require domain validation. The adapter must detect `status != completed`, absent `output_parsed`, and refusal content before returning a `RunnerOutput`.
3. **Build a versioned, instruction-separated request.** Keep a prompt template and `PROMPT_VERSION` constant in `app/ai/`, with explicit rules for observations versus hypotheses, no arithmetic, no invented figures, no unsupported comparison, metric ID references, and unavailable reasons. Serialize only the already bounded `PreparedContext` as a delimited data block, keeping objectives as untrusted user data; the prompt tells the model to ignore any instructions inside that block. Do not add pasted text or uploaded objects in this change. Keep model-specific request options minimal and supported by the configured model; use `OPENAI_MODEL`, not a hard-coded production model. Avoid sending owner IDs and internal job IDs if they are unnecessary to narrative generation; retain those in the trusted local context for validation and provenance. The alternative of sending raw source content would enlarge privacy and prompt-injection risk without improving the confirmed metric contract.
4. **Set a bounded provider request and trusted provenance.** Add validated `OPENAI_API_KEY` (secret), `OPENAI_MODEL`, and `OPENAI_TIMEOUT_SECONDS` settings and safe example environment names. Choose a timeout below `ANALYSIS_TASK_TIME_LIMIT_SECONDS` with room for database completion; reject an invalid configuration. Derive `RunnerOutput.model_identifier` from the provider response, `prompt_version` from the local prompt constant, and a compact safe `request_provenance` from the response identifier plus prompt/context version and a digest of the submitted context; never trust model-authored provenance. Existing job and result foreign keys link the outcome to the captured dataset and metric revision. Do not store the raw request or response. A client-supplied provenance field would be forgeable and is excluded.
5. **Map failures at the adapter boundary.** Provider timeout maps to retryable `provider_timeout`; transient transport, rate-limit, and server errors map to retryable `provider_unavailable`; explicit refusal maps to non-retryable `provider_refusal`; non-completed or absent parsed output maps to retryable `incomplete_response`; schema conversion or grounding failure maps to non-retryable `invalid_structured_output`; stale input maps to non-retryable `stale_result`. Unexpected SDK errors become sanitized `provider_unavailable` without exception text in public state or logs. Reuse `AnalysisExecutionFailure` and the existing `execute_analysis` claim, recheck, and completion transaction. No adapter-side database writes or automatic SDK retries that can exceed the task timeout; the logical retry command remains authoritative.
6. **Wire only the production task to the real runner.** Construct the adapter from validated worker settings in `analysis_task`, pass it to `execute_analysis`, and close its network client cleanly. Keep the injectable test runner and durable attempt transitions. A duplicate Celery delivery cannot pass the same ordinal claim twice; a late provider response fails the existing current-input recheck and cannot overwrite a newer draft or prior valid result. Configuration errors after a job is accepted become safe failed attempts. This uses the existing worker contract rather than introducing parallel orchestration.

## Risks / Trade-offs

- [Strict provider schema may differ from the internal Pydantic model] → Use the explicit wire DTO and conversion tests against the pinned SDK; retain domain validation after parsing.
- [A model can return schema-valid but unsupported prose] → Keep the existing numeric-text and reference validation, test invented values and foreign IDs, and fail the whole attempt rather than silently dropping an item.
- [Provider call completes after a revision change] → Recheck the complete semantic identity inside the completion transaction; preserve older results and fail stale attachment.
- [Provider timeout or SDK retry exceeds Celery's task limit] → Configure one bounded request with timeout below the task limit, disable hidden retry amplification, and keep stale-running recovery for process death.
- [Prompt or response data leaks through exceptions or telemetry] → Emit only safe identifiers and failure codes; test captured API bodies and logs for content and credential redaction.

## Migration Plan

1. Pin the SDK, add settings/example environment values, prompt and adapter, and wire the worker. No database migration is expected; if implementation proves one necessary, create an Alembic migration and verify upgrade and safe downgrade where possible.
2. Deploy worker configuration with `OPENAI_API_KEY`, `OPENAI_MODEL`, and the bounded timeout. Existing queued jobs can be reconciled and executed by the new worker; their captured input still must pass current-input checks.
3. Roll back the worker runner to the prior safe unavailable executor if provider integration fails. Durable jobs, attempts, and validated results remain in PostgreSQL; no data rewrite or status reset is required.
